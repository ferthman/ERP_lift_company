## 1. Общий обзор проекта

Lift CRM сейчас — это локальное Flask-приложение для одной лифтовой сервисной компании. Оно использует SQLite (`lift_crm.db`), SQLAlchemy-модели, Flask-Login, server-rendered Jinja + большой vanilla JS интерфейс, Tailwind CDN, Leaflet/OpenStreetMap и мобильное PWA для мастеров.

Текущая структура:

- `app.py` — тонкий entrypoint, вызывает `liftcrm.create_app()`.
- `liftcrm/__init__.py` — фабрика Flask-приложения, регистрация blueprints, первичная инициализация БД/файлов, маршруты страниц `/`, `/admin`, `/mobile`, `/lifts/<id>`, `/history`.
- `liftcrm/db.py` — модели, SQLAlchemy engine/session, `init_db()`, ручные SQLite-миграции `ensure_migrations()`.
- `liftcrm/tickets/` — заявки, статусы, SLA, назначение, архив, метрики, синхронизация PWA.
- `liftcrm/assets/` — реестр лифтов, клиенты, договоры, плановое ТО, история лифта.
- `liftcrm/access/` — управление пользователями, ролями, заменой мастера.
- `templates/index.html` — основной desktop-интерфейс для админа/диспетчера.
- `templates/mobile.html` + `static/mobile.js` — мобильное PWA мастера с offline outbox.
- `docs/` и `PLANS.md` — runbook, архитектурные заметки и история ExecPlan-работ.

Роли:

- `admin` — полный доступ, пользователи, мастера, метрики, заявки, лифты, клиенты, договоры, ТО.
- `dispatcher` — заявки, лифты, клиенты/договоры, ТО, карта, но без управления пользователями и dashboard admin-раздела.
- `technician` — мастерский мобильный поток `/mobile`, только свои заявки; старое значение `master` нормализуется в `technician`.

Основные сущности:

- `User`, `Master`
- `Ticket`
- `Asset` — фактически лифт/единица оборудования, сейчас также несет адрес объекта.
- `Customer`, `Contract`
- `MaintenancePlan`
- `TicketComment`, `Attachment`
- `AppliedEvent` для идемпотентной offline sync
- `AuditLog`

Краткий вывод: проект уже ближе всего к диспетчерской системе / service desk для лифтовой компании с CRM-элементами. Это еще не ERP: нет склада, финансов, договорного учета на уровне документов, регламентного обслуживания как отдельного факта работ, план-факт аналитики, полноценной структуры объект → лифты → история объекта. Но это уже больше, чем “просто база данных”: есть роли, жизненный цикл заявки, мастерское PWA, аудит, SLA, приоритеты, клиенты/договоры и плановое ТО.

## 2. Карта текущего функционала

### Объекты

Что есть сейчас:

- В UI есть вкладка `Объекты`, но технически она показывает `assets` на карте, то есть лифты/оборудование из SQL-реестра.
- Исторически есть `objects/objects.xlsx` и `objects/objects.json`; сейчас основной runtime уже переведен на таблицу `assets`.
- `/api/objects` существует как deprecated alias к `/api/assets`.
- На карте можно искать по адресу, серийному номеру, метке лифта, подъезду, клиенту и договору.
- Можно включить слой открытых заявок на карте.

Поля, которые реально хранятся на уровне `Asset`:

- `address`
- `address_norm`
- `entrance`
- `lift_label`
- `serial_no`
- `customer_id`
- `contract_id`
- `lat`, `lon`
- `status`
- `created_at`, `updated_at`

Что хорошо:

- Есть карта и поиск.
- Есть связь с клиентом и договором.
- Есть экспорт/import реестра лифтов.
- Есть открытие карточки лифта из списка.

Что не хватает:

- Нет отдельной сущности `Object` / `Building`.
- Нельзя открыть карточку объекта и увидеть все лифты объекта, все активные/закрытые заявки и контактных лиц.
- Адрес объекта дублируется в `Asset` и `Ticket`, но не нормализован как отдельная запись.
- История объекта не реализована: есть история конкретного лифта, но не агрегированная история здания/объекта.
- `objects.xlsx/json` остаются как legacy-след, что может путать операторов и разработчиков.

### Лифты

Что есть сейчас:

- Лифт представлен моделью `Asset`.
- CRUD через `/api/assets` доступен admin/dispatcher.
- UI вкладка `Лифты` содержит список, поиск, импорт CSV/XLSX, экспорт XLSX/CSV, модальное создание/редактирование.
- Карточка лифта доступна по `/lifts/<asset_id>`.
- История лифта доступна через `/api/lifts/<asset_id>/history` и отображается в `templates/lift_detail.html` + `static/lift_detail.js`.

Данные лифта:

- адрес;
- подъезд;
- метка лифта;
- серийный номер;
- координаты;
- статус `ACTIVE/INACTIVE`;
- клиент;
- договор.

История по лифту:

- Собирает заявки по `Ticket.asset_id`.
- Показывает события из `AuditLog`, комментарии `TicketComment`, вложения `Attachment`.
- Считает метрики реакции, ремонта и ожидания.
- Есть фильтр по дате и поиску.

Что хорошо:

- Это сильная часть проекта: связь `лифт → заявки → события` уже реализована.
- История опирается не только на текущий статус, но и на audit log/comment/photo events.

Что улучшить:

- Инфо-вкладка карточки лифта сейчас почти пустая: “Раздел для дополнительной информации о лифте”.
- Нет паспортных данных лифта: тип, модель, грузоподъемность, этажность, дата ввода, обслуживающая зона, регламент.
- Нет документов и фото самого лифта отдельно от фото заявок.
- Нет QR-кода на лифт.
- Нет явного состояния лифта “нормально / есть активная авария / проблемный / на ТО”; его можно вывести из заявок, но не как отдельный понятный показатель.
- Плановое ТО хранится отдельно в `MaintenancePlan`, но история ТО не объединена в карточке лифта как отдельная вкладка “ТО/обслуживание”.

### Заявки

Как создаются:

- Desktop форма в `templates/index.html`, endpoint `POST /api/tickets`.
- Создавать могут `admin` и `dispatcher`.
- Можно выбрать лифт через asset autocomplete; если лифт выбран, адрес/координаты могут подставляться.
- Если лифт не выбран, нужно вручную ввести объект, lat/lon или выбрать точку на карте.
- После создания система пытается автоназначить активного мастера через `auto_assign_master()`.

Поля заявки:

- `object_name`
- `address`
- `lat`, `lon`
- `description`
- `status`
- `version`
- `priority`
- `assigned_master_id`, `assigned_at`
- timestamps: `created_at`, `updated_at`, `accepted_at`, `arrived_at`, `waiting_at`, `completed_at`, `cancelled_at`, `archived_at`
- `waiting_reason`
- `arrival_lat/lon`, `completion_lat/lon`
- `close_reason`, `close_comment`
- `custom_sla_response_minutes`, `custom_sla_completion_minutes`
- `email`
- `asset_id`
- `maintenance_plan_id`, `maintenance_due_date`

Статусы:

- `NEW`
- `ASSIGNED`
- `ACCEPTED`
- `IN_PROGRESS`
- `WAITING`
- `COMPLETED`
- `CANCELLED`

Приоритеты:

- `EMERGENCY`
- `HIGH`
- `MEDIUM`
- `LOW`

Для `EMERGENCY` и `HIGH` автоматически задаются более строгие SLA, если диспетчер не указал кастомные SLA.

Назначение мастера:

- Автоназначение выбирает активного мастера с активным technician-пользователем и минимальной нагрузкой по открытым заявкам.
- Ручное назначение есть через `POST /api/tickets/<id>/assign/<master_id>`.
- При деактивации/удалении мастера открытые заявки перераспределяются.

Комментарии:

- Таблица `ticket_comments` есть.
- Мобильное PWA умеет добавлять комментарий через offline event `TICKET_ADD_COMMENT`.
- Desktop ticket modal показывает историю, но в desktop UI нет полноценного поля “добавить комментарий” для диспетчера.

Вложения/фото:

- Таблица `attachments` есть.
- Endpoint `/api/tickets/<id>/upload` принимает `png/jpg/jpeg/webp`.
- Мобильное PWA умеет ставить фото в offline queue и загружать после восстановления сети.
- Desktop UI показывает ссылки на файлы, но desktop upload UX не является центральным сценарием.

История изменений:

- `AuditLog` фиксирует создание, назначение, редактирование, отмену, архивирование, статусные изменения, создание комментариев и вложений.
- `/api/tickets/<id>/history` показывает историю по заявке.
- В ticket modal на desktop история подгружается.

Фильтры и поиск:

- В списке заявок есть фильтры: SLA overdue, мастер, приоритет.
- В Kanban есть группировка по статусам.
- В history page есть фильтр по датам и статусам.
- Нет полноценного поиска по тексту заявки, телефону, клиенту, адресу, серийному номеру прямо в списке заявок.

Удобство для диспетчера:

- Базовый поток работает, но создание заявки еще слишком “техническое”: координаты, карта, object_name, address, SLA-поля и таблица шириной много колонок.
- Для реального диспетчера нужен режим “быстрый звонок”: одно поле поиска объекта/лифта, проблема, контакт, приоритет, назначить/создать.

Удобство для мастера:

- Сильная часть: `/mobile` показывает только свои заявки, поддерживает offline cache/outbox, статусы, комментарии, фото и 2GIS.
- Нет списания запчастей, чек-листов, QR-открытия лифта, истории именно этого лифта перед выездом в мобильном интерфейсе.

### Пользователи и роли

Что есть:

- `admin`, `dispatcher`, `technician`.
- Admin управляет пользователями и мастерами во вкладке `Пользователи и допуск`.
- Можно включать/отключать пользователей, менять роль, менять пароль, назначать technician-доступ мастеру, заменять сотрудника с переносом открытых заявок.
- `role_required()` проверяет роли на backend.

Что хорошо:

- Разделены учетная запись (`User`) и профиль мастера (`Master`).
- Для technician требуется `master_id`.
- Есть уникальный индекс `ux_users_master_id`, который ограничивает одного user на один master.

Что не хватает:

- Нет отдельной таблицы ролей/permissions.
- Нет настройки прав на уровне “диспетчер может/не может редактировать лифты/договоры/ТО”.
- Нет роли “руководитель” отдельно от admin.
- Нет аудит-экрана по действиям пользователей.

### Клиенты / ОСИ / КСК / управляющие компании

Что есть:

- `Customer`: `name`, `contact_person`, `phone`, `email`, `notes`, `is_active`, timestamps.
- `Contract`: `customer_id`, `contract_number`, `title`, `start_date`, `end_date`, `status`, SLA hours, notes, timestamps.
- `Asset` привязывается к `Customer` и `Contract`.
- Ticket serializer выводит customer/contract context через связанный лифт.

Что хорошо:

- Для B2B-лифтовой компании это правильное направление.
- Клиент/договор отображаются в лифте, карте, заявке, ТО.

Что не хватает:

- Нет отдельных контактных лиц как списка.
- Нет истории взаимодействий с клиентом.
- Нет документов договора.
- Нет финансового статуса.
- SLA из договора пока справочные: ticket SLA не рассчитывается автоматически из `Contract.sla_hours_*`.
- Заявка не хранит исторический snapshot клиента/договора; если лифт перепривязали к другому договору, старые заявки будут показывать актуальную связь, а не связь на момент заявки.

### Склад / запчасти

Склада сейчас нет:

- нет `SparePart`;
- нет `InventoryTransaction`;
- нет списания запчастей в заявке;
- нет остатков;
- нет прихода/расхода;
- нет связи “запчасть использована в заявке”.

Рекомендация: не делать склад P0, если цель — быстро запустить диспетчеризацию и историю. Но для полноценной сервисной компании склад станет P1/P2 после стабилизации заявок, истории и мобильного мастера.

### Отчеты и аналитика

Что есть:

- `/api/metrics`: количество заявок, статусы, среднее/медианное время закрытия, SLA breaches, причины закрытия, приоритеты, данные по мастерам.
- Admin UI `Дашборд выполнения`.
- `GET /api/archive` экспортирует все заявки в XLSX.
- Реестр лифтов экспортируется в CSV/XLSX.
- История заявок `/history`.
- История лифта `/lifts/<id>`.

Что не хватает:

- “Проблемные лифты” по повторным заявкам.
- “Проблемные объекты” по сумме лифтов.
- Отчет по заявкам по объектам/клиентам/договорам.
- Отчет по просроченным SLA с датами и ответственными.
- Отчет по мастерам с корректной UI-таблицей.
- Time series по дням/неделям.
- PDF/Excel настраиваемые отчеты.
- Отчет по плановому ТО.

Найденный дефект: API `/api/metrics` возвращает по мастерам поля `name`, `total`, `avg_close_sec`, `median_close_sec`, а UI в `templates/index.html` рендерит `row.master_name`, `row.count`, `row.avg_sec`, `row.median_sec`. В результате таблица “Топ мастеров” будет показывать пустые/undefined значения.

Честный вывод:

- Использовать систему в реальной компании уже можно как пилот для диспетчеризации заявок, назначения мастеров и сбора истории по лифтам.
- Полноценно запускать как “готовую CRM” рискованно: нет объектной модели, не хватает быстрой заявки, object-level истории, production backup/deployment процесса, части отчетов и UX-полировки.
- Критично до запуска: быстрый create flow, нормальная карточка объекта, комментарии диспетчера, исправление UI-метрик, индексы/миграции, backup-процедура.
- Позже можно добавить склад, финансы, договорные документы, SMS/push, QR-коды, полноценные ERP-модули.

## 4. Аудит хранения данных и базы

### Как сейчас хранятся данные

Основное хранилище — SQLite файл `lift_crm.db`. Таблицы создаются SQLAlchemy `Base.metadata.create_all(engine)` и дополняются ручной функцией `ensure_migrations()` в `liftcrm/db.py`.

Текущие таблицы:

- `users`
- `masters`
- `tickets`
- `assets`
- `customers`
- `contracts`
- `maintenance_plans`
- `attachments`
- `ticket_comments`
- `applied_events`
- `audit_log`

Текущие связи:

- `users.master_id → masters.id`
- `tickets.assigned_master_id → masters.id`
- `tickets.asset_id → assets.id`
- `tickets.maintenance_plan_id → maintenance_plans.id` в модели, но в текущей SQLite schema FK на `maintenance_plan_id` не отображается.
- `assets.customer_id → customers.id` в модели; текущая SQLite schema имеет колонку, но FK constraint не отображается.
- `assets.contract_id → contracts.id` в модели; текущая SQLite schema имеет колонку, но FK constraint не отображается.
- `contracts.customer_id → customers.id`
- `maintenance_plans.asset_id → assets.id`
- `maintenance_plans.assigned_master_id → masters.id`
- `attachments.ticket_id → tickets.id`
- `ticket_comments.ticket_id → tickets.id`
- `ticket_comments.user_id → users.id`
- `audit_log.actor_user_id → users.id`

### Объект → лифт → заявка → история

Сейчас фактическая цепочка такая:

`Asset (лифт + адрес объекта) → Ticket → AuditLog/TicketComment/Attachment`

Это работает для истории лифта, но не является нормальной объектной структурой. Нет отдельного уровня `Building/Object`, поэтому несколько лифтов по одному адресу нельзя надежно сгруппировать в карточку объекта с общей историей.

### Дублирование и слабые места

- `Ticket` хранит `object_name`, `address`, `lat`, `lon` даже если связан с `Asset`. Это удобно для snapshot, но сейчас нет четкого правила: какие поля являются историческим снимком, а какие должны подтягиваться из лифта.
- `Customer/Contract` в заявке не snapshot-ятся, а выводятся из текущей связи `ticket.asset`. Это может искажать старую историю после перепривязки лифта к другому договору.
- `Asset` одновременно означает лифт, оборудование и адрес объекта.
- Legacy `objects/objects.xlsx/json` существует рядом с SQL `assets`, хотя реальный runtime уже использует SQL.
- В `uploads/` есть файлы при `attachments=0`; нужна уборка сиротских файлов и backup policy.
- Вручную поддерживаемые SQLite-миграции сложнее контролировать, чем Alembic-style migration history.

### Названия полей

Что оставить:

- `Ticket`, `Asset`, `MaintenancePlan`, `Customer`, `Contract` можно оставить в коде на текущем этапе.

Что переименовать или уточнить:

- UI и docs должны последовательно называть `Asset` как “Лифт” или “Единица оборудования”.
- `object_name` в заявке лучше переосмыслить как `title` или `request_title`; объект должен быть отдельным `building_id`.
- `technician` и “мастер” в UI должны быть единообразно объяснены: backend role `technician`, business label “Мастер”.
- `MaintenancePlan.status = overdue` лучше убрать как ручной persisted status; просрочка уже корректнее рассчитывается как derived `due_status`.

### Индексы

В текущей live schema есть индексы:

- `assets.serial_no`
- `assets.address`
- `assets.address_norm`
- `assets.lat, lon`
- `assets.customer_id`
- `assets.contract_id`
- `audit_log(entity_type, entity_id, created_at)`
- `users.master_id` unique partial

Слабое место: нет индексов на самые частые ticket-запросы:

- `tickets(asset_id, created_at)`
- `tickets(assigned_master_id, status, archived_at)`
- `tickets(status, created_at)`
- `tickets(priority, status)`
- `tickets(maintenance_plan_id, maintenance_due_date, status)`
- `ticket_comments(ticket_id, created_at)`
- `attachments(ticket_id, created_at)`
- `maintenance_plans(asset_id, next_due_date, status)`
- `maintenance_plans(assigned_master_id, status, next_due_date)`
- `contracts(customer_id, status)`

Отдельно: в `ensure_migrations()` индексы `idx_maintenance_plans_asset_id` и `idx_maintenance_plans_next_due_date` создаются только в ветке, где таблица `maintenance_plans` создается вручную. Если таблица уже создана через `Base.metadata.create_all()`, эти индексы могут не появиться. В текущей live schema они не отображаются.

### История, аудит и восстановление “кто и когда”

Что есть:

- `AuditLog` фиксирует diff по заявкам и некоторым связанным событиям.
- `TicketComment` хранит `user_id`.
- `Attachment` creation логируется как audit event.
- `AppliedEvent` защищает offline sync от дублей.

Что не хватает:

- В основных таблицах нет `created_by`, `updated_by`.
- `AuditLog.created_at` хранится как `String`, а не `DateTime`.
- Аудит неполный: изменения `Asset`, `Customer`, `Contract`, `MaintenancePlan` не логируются как полноценная история.
- Нет глобального audit UI для администратора.
- Нет request metadata: IP, user agent, source (`desktop/mobile/sync`).
- Нет отдельной таблицы `RequestStatusHistory`, из-за чего восстановление lifecycle зависит от audit diff.

### Soft delete / архивирование

Есть:

- `tickets.archived_at` — soft archive.
- `DELETE /api/tickets/<id>` deprecated и возвращает 405.
- `Asset` “удаляется” переводом в `INACTIVE`.
- `Customer.is_active`.
- `Contract.status`.

Нет:

- Архивирования комментариев/вложений/maintenance plans.
- Политики удаления файлов.
- Отдельной ротации архива XLSX.

### Рекомендуемая структура данных

Минимально правильная структура для CRM лифтовой компании:

| Сущность | Нужна? | Рекомендация |
|---|---:|---|
| `Company` | Позже / singleton | Для одной компании не нужен multi-tenancy, но нужен singleton для настроек: название, SLA defaults, контакты, backup policy |
| `User` | Да | Оставить |
| `Role` | Не P0 | Пока enum достаточно; permissions-таблица нужна при росте |
| `Building/Object` | Да, P0 | Добавить отдельную карточку объекта: адрес, клиент, контакты, координаты, notes |
| `Elevator` / `ElevatorUnit` | Да | Текущий `Asset` превратить в понятный Elevator/Equipment layer |
| `ServiceRequest/Ticket` | Да | Оставить, но добавить `building_id`, historical snapshots и source/contact fields |
| `RequestStatusHistory` | Да, P0/P1 | Сделать явную статусную историю вместо вычисления только из audit log |
| `RequestComment` | Да | Текущий `TicketComment` оставить, добавить desktop UX |
| `RequestAttachment` | Да | Текущий `Attachment` оставить, добавить типы фото |
| `MaintenanceVisit` | Да, P1 | Отдельный факт выполненного ТО, не только `MaintenancePlan.complete` |
| `SparePart` | P1/P2 | После запуска заявок |
| `InventoryTransaction` | P1/P2 | После появления склада |
| `ClientOrganization` | Да | Текущий `Customer`, лучше назвать business-термином |
| `ContactPerson` | P1 | Несколько контактов на объект/клиента |
| `Notification` | P1/P2 | Для push/SMS/email/escalation |
| `AuditLog` | Да | Расширить на все важные сущности |

## 5. Аудит интерфейса

### Для диспетчера

Текущее состояние:

- Диспетчер попадает на вкладку `Панель`, где слева форма создания заявки, справа таблица заявок.
- Создание можно сделать быстро, если лифт уже есть в `assets` и у него есть координаты.
- Если лифта нет, нужно вручную вводить объект, адрес, lat/lon или пользоваться картой.
- Активные заявки видны в таблице и Kanban.
- Срочность видна через priority badges.
- Назначение мастера есть, но выполняется через кнопку “Назначить” в строке, которая раскрывает select.
- Статусные переходы в основном делает мастер; диспетчер может назначить, отменить, архивировать, редактировать priority/SLA/description.

Оценка:

- Для пилота приемлемо.
- Для реальной диспетчерской линии интерфейс слишком широкий и технический.
- Ключевая проблема: оператору приходится думать о координатах, SLA overrides, карте и таблице, хотя при звонке ему нужен быстрый поиск лифта и минимум полей.

Рекомендации:

- Сделать отдельный экран “Новая заявка” или верхний быстрый drawer:
  - одно поле: адрес / лифт / серийник / клиент;
  - активные заявки по найденному лифту сразу рядом;
  - проблема из шаблона + свободный текст;
  - контакт/телефон заявителя;
  - приоритет;
  - мастер: авто / выбрать;
  - кнопка “Создать”.
- Добавить duplicate warning: “по этому лифту уже есть активная заявка”.
- Добавить сохраненные фильтры: “новые”, “аварийные”, “без мастера”, “просроченные SLA”, “мои на контроле”.
- Перевести English labels в UI: `active`, `paused`, `monthly`, `overdue only`, `Response`, `Completion`, `SLA breach`.
- Сузить таблицу заявок и вынести подробности в карточку/панель.

### Для мастера

Текущее состояние:

- `/mobile` доступен только `technician`.
- Мастер видит свои заявки через `/api/me/tickets`.
- Есть offline cache через IndexedDB.
- Есть offline outbox для статусов, комментариев и фото.

- Есть ссылка 2GIS.
- Есть история закрытых заявок мастера и timeline по заявке.

Оценка:

- Это одна из самых сильных частей проекта.
- Для реальных мастеров уже близко к полезному мобильному приложению.

Проблемы:

Рекомендации:

### Для администратора

## 7. Что можно убрать или упростить

### Точно убрать после миграции

- Legacy `objects/objects.xlsx/json` как runtime-источник. Сейчас они дублируют идею SQL `assets` и могут путать. Лучше оставить только как импортный пример или удалить после переноса.
- Deprecated `/api/objects`, если нет внешних клиентов. Если есть риск совместимости, оставить временно, но явно документировать срок удаления.

### Временно скрыть

- Кастомные SLA-поля из основной формы создания. Они нужны не при каждом звонке; лучше спрятать в “Дополнительно”.
- Ручной persisted status `overdue` в форме ТО. Просрочка должна быть derived.
- `LOW` priority можно оставить в API, но в UI для диспетчера показывать как “Планово/не срочно” только в advanced.
- Кнопку `Моя геолокация` в форме диспетчера: она полезна для тестов, но в реальной диспетчерской чаще нужна геолокация объекта, а не диспетчера.

### Объединить

- `Панель` + `Контроль этапов` можно объединить в раздел `Заявки` с режимами “Список” и “Kanban”.
- `Админ` dashboard лучше переименовать в `Отчеты` или `Dashboard`.
- `Объекты` карта и `Лифты` реестр должны быть связаны через карточку объекта: карта — это способ навигации, а не отдельная бизнес-сущность.

### Оставить, но упростить

- Плановое ТО: оставить, но перевести labels на русский и убрать лишний ручной статус.
- Клиенты/договоры: оставить, но вынести в отдельный раздел после появления object card.
- Таблицу заявок: оставить как power-user view, но сделать compact list по умолчанию.

## 9. Идеальная логика заявки

Рекомендованный lifecycle:

1. `Новая`
2. `Назначена`
3. `Принята мастером`
4. `В пути`
5. `На объекте`
6. `В работе`
7. `Ожидает запчасть` / `Ожидает доступ` / `Ожидает клиента`
8. `Выполнена мастером`
9. `Закрыта диспетчером`
10. `Отменена`

Что есть сейчас:

- `NEW`
- `ASSIGNED`
- `ACCEPTED`
- `IN_PROGRESS`
- `WAITING`
- `COMPLETED`
- `CANCELLED`

Текущие отличия:

- `В пути` отсутствует.
- `На объекте` и `В работе` объединены в `IN_PROGRESS`.
- `Ожидает запчасть` не отдельный статус; есть общий `WAITING` + `waiting_reason`.
- Нет финального `CLOSED` после проверки диспетчером; `COMPLETED` означает завершил мастер.
- Архивирование (`archived_at`) отдельно от бизнес-статуса.

Что оставить сейчас:

- Существующие enum-коды до крупного миграционного шага.
- Строгую функцию `validate_status_transition()`.
- `WAITING` с reason как быстрый MVP-путь.

Что добавить:

- `CLOSED` как диспетчерское закрытие после `COMPLETED`.
- `waiting_category`: `PARTS`, `ACCESS`, `CUSTOMER`, `OTHER`.
- Позже разделить `EN_ROUTE` и `ON_SITE`, если бизнес реально будет этим пользоваться.

Рекомендуемые переходы:

| Из | В | Кто |
|---|---|---|
| `NEW` | `ASSIGNED` | dispatcher/admin/system |
| `NEW` | `CANCELLED` | dispatcher/admin |
| `ASSIGNED` | `ACCEPTED` | technician |
| `ASSIGNED` | `ASSIGNED` | dispatcher/admin reassign |
| `ACCEPTED` | `EN_ROUTE` | technician |
| `EN_ROUTE` | `ON_SITE` | technician + geofence |
| `ON_SITE` | `IN_PROGRESS` | technician |
| `IN_PROGRESS` | `WAITING` | technician |
| `WAITING` | `IN_PROGRESS` | technician |
| `IN_PROGRESS` | `COMPLETED` | technician |
| `COMPLETED` | `CLOSED` | dispatcher/admin |
| Любой открытый | `CANCELLED` | dispatcher/admin |

Что логировать:

- создание;
- назначение/переназначение;
- каждый status transition;
- изменение priority/SLA/описания;
- комментарии;
- вложения;
- geofence facts;
- отмену с причиной;
- закрытие диспетчером;
- архив/разархив;
- создание из ТО;
- использованные запчасти, когда появится склад.

## 12. Финальный executive summary

Готовность:

- Проект готов к ограниченному пилоту внутри одной компании для учета заявок, назначения мастеров, мобильной работы и истории по лифтам.
- Проект не готов как полноценная CRM/ERP без доработок объектной модели, UX создания заявки, отчетов и production-операций.

Главные сильные стороны:

1. Есть рабочий lifecycle заявок и backend validation переходов.
2. Есть роли admin/dispatcher/technician.
3. Есть mobile PWA с offline outbox, фото и геозоной.
4. Есть реестр лифтов и история по лифту.
5. Есть audit log, SLA, приоритеты, клиенты/договоры и плановое ТО.
6. Автотесты проходят: `150 passed, 6 subtests passed`.

Главные слабые стороны:

1. Нет отдельной сущности объекта/здания.
2. Быстрое создание заявки пока перегружено техническими полями.
3. Object-level история отсутствует.
4. Desktop-комментарии не доведены до полноценного диспетчерского flow.
5. Метрики мастеров в UI сейчас читают не те поля API.
6. Склад/запчасти отсутствуют.
7. Миграции и индексы требуют усиления.

Главные риски:

- Потеря или порча локальных данных без дисциплины backup.
- Рост SQLite-файла и замедление запросов без индексов.
- Неполная история клиента/договора из-за отсутствия snapshot на заявке.
- Путаница между “объектом” и “лифтом” в данных.
- Перегрузка интерфейса для диспетчера.

5 самых важных улучшений:

1. Быстрый экран создания заявки.
2. `Building/Object` + карточка объекта.
3. Desktop-комментарии и улучшенная карточка заявки.
4. Исправить metrics UI и добавить проблемные лифты/объекты.
5. Индексы + migration hardening + backup routine.

Что сделать первым делом:

- Начать с object model и быстрого создания заявки, потому что это напрямую закрывает главные бизнес-требования: быстро создать заявку, видеть историю по объекту и быстро найти нужный лифт.

Что не стоит делать сейчас:

- Не строить полноценный ERP-склад/финансы до стабилизации CRM-ядра.
- Не делать multi-company/SaaS.
- Не усложнять роли до fine-grained RBAC, пока достаточно трех ролей.
- Не добавлять тяжелый календарь ТО, пока date-grouped queue покрывает MVP.
