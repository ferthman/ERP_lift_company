# Runbook — Lift CRM

## Быстрый старт (локально)
1) Зависимости: `python -m pip install -r requirements.txt` (Python 3.11+).【F:requirements.txt†L1-L8】  
2) Запуск: `python app.py` (поднимает Flask dev-server на `http://127.0.0.1:5000`).【F:app.py†L773-L804】  
3) Аккаунты для входа:
   - admin / `admin123`
   - dispatcher / `disp123`
   - Доступ мастеров назначается вручную через страницу «Пользователи и допуск» (админ создаёт профиль мастера и назначает роль TECHNICIAN).【F:templates/index.html†L203-L334】

## Что создаётся автоматически

- Каталог `uploads/` для файлов вложений и таблица `assets` в SQLite (создаётся миграцией при первом запросе).【F:liftcrm/db.py†L95-L142】
- Файл `archive.xlsx` (пустой с заголовками, включая колонку priority) для скачивания архива заявок.【F:liftcrm/__init__.py†L68-L104】

## Локальный backup/restore для MVP-пилота
Это простая страховка для локального MVP на SQLite. Она не заменяет production backup-архитектуру, не решает отказоустойчивость сервера и не предназначена для Docker/Postgres/deployment-сценариев.

### Что сохранять перед каждым пилотным днём
- `lift_crm.db` — основная SQLite-база.
- `uploads/` — вложения и фото заявок.
- `archive.xlsx`, `archive_*.xlsx`, `*export*.xlsx`, `*export*.csv` — локальные архивные и экспортные файлы, если они есть.

### Создать backup
1. Остановите локальный Flask-сервер, чтобы SQLite и файлы не менялись во время копирования.
2. Из корня проекта выполните:
   ```bash
   python scripts/backup_local.py
   ```
3. Скрипт создаст папку вида `backups/20260523-180000/` и файл `manifest.json`.
4. Проверьте вывод: предупреждения о отсутствующих `uploads/` или archive/export файлах допустимы, если этих данных ещё нет.

### Восстановить backup
1. Остановите локальный Flask-сервер.
2. Сначала попробуйте восстановление без перезаписи:
   ```bash
   python scripts/restore_local.py backups/20260523-180000
   ```
3. Если скрипт сообщает, что текущие локальные данные уже существуют, создайте свежий backup текущего состояния и только потом выполните:
   ```bash
   python scripts/restore_local.py backups/20260523-180000 --force
   ```
4. `--force` перезаписывает `lift_crm.db`, заменяет `uploads/` содержимым из backup и перезаписывает совпадающие archive/export файлы из backup.

### Проверить восстановление
1. Запустите приложение: `python app.py`.
2. Войдите как admin и проверьте, что заявки, мастера, assets/объекты и архивные данные соответствуют выбранному backup.
3. Откройте несколько вложений из заявок и убедитесь, что файлы из `uploads/` доступны разрешённым пользователям.
4. Скачайте архив через интерфейс или `GET /api/archive` и проверьте, что файл создаётся/отдаётся без ошибки.

## Приоритеты заявок
- Enum: EMERGENCY («Аварийная»), HIGH («Высокая»), MEDIUM («Обычная», значение по умолчанию), LOW («Низкая»). Для совместимости API также принимает aliases `emergency`/`urgent`, `high`, `normal`/`medium`, `low`; `normal` сохраняется как MEDIUM.【F:liftcrm/tickets/routes.py†L20-L27】【F:liftcrm/db.py†L46-L77】
- Установка при создании: поле «Приоритет» в форме тикета; бэкенд нормализует строку enum/alias, иначе 400. Дефолт — MEDIUM. Для EMERGENCY без ручного SLA ставится целевой SLA 5/60 минут, для HIGH — 15/90 минут; ручные SLA поля диспетчера имеют приоритет.【F:liftcrm/tickets/routes.py†L174-L202】【F:templates/index.html†L33-L69】
- Изменение после создания: админ/диспетчер → таблица заявок → выпадающий список, отправляется `PATCH /api/tickets/{id}` с новым приоритетом.【F:liftcrm/tickets/routes.py†L204-L236】【F:templates/index.html†L285-L334】
- Отображение: таблица, канбан, карточки мастера и метрики показывают цветовые бейджи; EMERGENCY выделяется красным и поднимается выше обычных заявок в активных списках, HIGH — янтарным, MEDIUM/LOW — нейтральными стилями.【F:templates/index.html†L270-L334】【F:templates/index.html†L335-L380】【F:templates/index.html†L360-L421】【F:templates/index.html†L616-L647】

### Аварийные и высокоприоритетные заявки
Используйте EMERGENCY, когда есть непосредственный риск для людей или серьёзная эксплуатационная угроза:
- застрявший пассажир;
- остановившийся лифт на критичном объекте;
- признаки угрозы безопасности;
- повторная авария после недавнего ремонта;
- срочная эскалация от клиента или диспетчерской службы.

Используйте HIGH для важных инцидентов без немедленной угрозы людям: повторяющиеся сбои, важный клиент, объект с высоким трафиком, просроченная реакция подрядчика.

Рекомендуемый операционный порядок для EMERGENCY:
1. Заполнить объект/адрес и понятное описание проблемы.
2. Указать контактные данные в существующих полях, если они доступны в текущей карточке.
3. Назначить мастера сразу, если диспетчер уже знает ближайшего доступного специалиста.
4. Уточнить по телефону факт риска для пассажиров/объекта и держать связь до принятия мастером.
5. После закрытия проверить причину закрытия и комментарий, чтобы история была полезна для разбора.

Как проверить видимость:
1. Войти как dispatcher/admin и создать заявку с приоритетом «Аварийная / срочная».
2. Убедиться, что `/api/tickets` возвращает `priority: "EMERGENCY"` и заявка выше обычных активных заявок.
3. В таблице и канбане проверить красный бейдж «Аварийная».
4. Войти назначенным мастером, открыть `/mobile` и проверить, что заявка в списке и деталях показывает приоритет «Аварийная».
5. Изменить приоритет через таблицу и открыть историю заявки: изменение должно быть в audit log как `EDIT`.

Ограничения текущего workflow:
- Нет автоматических push/SMS/звонков и отдельного escalation engine.
- Система не выбирает ближайшего мастера по геолокации; автоназначение по-прежнему использует текущую логику нагрузки.
- SLA-флаги показывают просрочку, но не отправляют уведомления сами по себе.
- LOW остаётся для совместимости со старыми заявками и фильтрами.

## SLA: контроль ответа и завершения
- SLA ответа = `created_at` → `arrived_at`; SLA завершения = `created_at` → `completed_at`.
- Дедлайны считаются динамически из `SLA_RESPONSE_MINUTES` и `SLA_COMPLETION_MINUTES`; по умолчанию 30/120 минут, можно переопределять через переменные окружения.
- **Перекрытие по тикету:** admin/dispatcher могут задать `custom_sla_response_minutes` и/или `custom_sla_completion_minutes` (целые >0) при создании/редактировании заявки. Эти поля перекрывают значения конфига только для выбранного тикета. Поля скрыты для мастера и доступны через форму создания/таблицу (кнопка «Сохранить» рядом с заявкой). В API `PATCH /api/tickets/{id}` можно передавать только SLA поля (priority становится опциональным).【F:liftcrm/tickets/routes.py†L174-L240】【F:templates/index.html†L33-L78】【F:templates/index.html†L268-L334】
- Нарушение фиксируется, если время факта позже дедлайна или если факт отсутствует, а текущее время уже вышло за срок. Флаги отображаются в таблице заявок, карточках канбана/дашборда и выгружаются в `archive.xlsx` (добавлены колонки custom_sla_*).【F:liftcrm/tickets/repository.py†L10-L68】【F:liftcrm/tickets/routes.py†L390-L421】
- API `/api/metrics` отдаёт счётчики и проценты нарушений, UI показывает их в блоке «Дашборд выполнения».
- При завершении тикета мастер обязан выбрать `close_reason` из списка (EQUIPMENT_FAILURE/PASSENGER_TRAPPED/FALSE_CALL/POWER_ISSUE/EXTERNAL_REASON/OTHER); поле отражается в API, метриках и выгрузке архива.【F:liftcrm/tickets/routes.py†L184-L241】【F:templates/index.html†L373-L421】

## Архивация заявок (soft-delete)
- `DELETE /api/tickets/{id}` больше не удаляет строку из БД, а проставляет `archived_at`; вложения остаются, запись скрывается из активного списка.【F:liftcrm/tickets/routes.py†L360-L372】
- `GET /api/tickets` по умолчанию отдаёт только активные заявки; добавьте `?include_archived=1`, чтобы увидеть архивированные (для админа/диспетчера).【F:liftcrm/tickets/routes.py†L153-L162】
- Экспорт `GET /api/archive` выгружает все заявки (активные + архив) и отдельные столбцы `archived_at` и `close_reason` в XLSX.【F:liftcrm/tickets/routes.py†L390-L433】
- При запуске выполняется миграция SQLite: колонка `archived_at` добавляется автоматически, если её ещё нет.【F:liftcrm/db.py†L107-L125】

## Клиенты и договоры
Клиент — это компания, управляющая организация, владелец здания или другой контрагент, к которому относится обслуживаемый лифт. Договор — сервисное соглашение клиента, покрывающее один или несколько лифтов. Это MVP-контекст для диспетчеризации, а не биллинг или расчёт тарифов.

### Создать клиента
1. Войти как admin или dispatcher.
2. Открыть вкладку «Лифты».
3. В блоке «Клиенты» заполнить «Название клиента». Остальные поля: контакт, телефон, email, заметки и активность.
4. Нажать «Сохранить клиента». Клиент появится в списке и будет доступен в карточке лифта.

### Создать договор
1. Сначала создайте клиента.
2. В блоке «Договоры» выберите клиента.
3. Заполните название договора, при необходимости номер, даты, статус и SLA-часы.
4. Статусы договора: `active`, `paused`, `expired`. Просроченные и приостановленные договоры остаются видимыми для истории.
5. Даты должны быть в порядке: дата окончания не раньше даты начала. SLA-часы, если указаны, должны быть положительными числами.

### Связать лифт с клиентом и договором
1. Во вкладке «Лифты» нажмите «Добавить лифт» или «Редактировать».
2. Выберите клиента и договор в карточке лифта.
3. Сохраните. API `GET /api/assets` начнёт возвращать `customer_id`, `customer_name`, `contract_id`, `contract_title`, `contract_number` и `contract_status`.
4. Договор должен принадлежать выбранному клиенту. Если выбран только договор, клиент выводится из договора автоматически.

### Как это влияет на заявки
- Заявка хранит существующую связь с лифтом через `asset_id`.
- Клиент и договор в заявке сейчас выводятся из связанного лифта, а не копируются в отдельные поля заявки.
- В таблице заявок и модальном окне заявки отображается контекст клиента/договора, если заявка связана с лифтом.
- Старые заявки без лифта или без привязки лифта к клиенту продолжают работать и показывают пустой контекст.

### Ограничения MVP
- Нет счетов, платежей, тарифов и расчёта стоимости.
- Нет автоматического SLA escalation engine; договорные SLA-часы пока справочные.
- Импорт лифтов не создаёт клиентов/договоры. Импортированные лифты можно связать с клиентом и договором после загрузки.
- Исторический snapshot клиента/договора в самой заявке не хранится; для этого нужен отдельный продуктовый шаг.

### Импорт лифтов из CSV/XLSX
Перед большим импортом сделайте локальный backup: `python scripts/backup_local.py`. Это позволит вернуться к прежнему `lift_crm.db`, если файл был подготовлен неверно.

Поддерживаемые файлы:
- `.csv` в UTF-8, первая строка — заголовки.
- `.xlsx`, первый лист, первая строка — заголовки.
- Файл читается из памяти и не сохраняется в `uploads/` или на диск.

Поддерживаемые поля и aliases:
- `address`: `address`, `object`, `object_name`, `объект`, `адрес` — обязательное поле.
- `entrance`: `entrance`, `подъезд`.
- `lift_label`: `lift_label`, `lift`, `elevator`, `elevator_label`, `лифт`, `метка лифта`.
- `serial_no`: `serial_no`, `serial`, `заводской номер`, `серийный номер`.
- `lat`: `latitude`, `lat`, `широта`.
- `lon`: `longitude`, `lng`, `lon`, `долгота`.
- `status`: `status`, `статус`; допустимо только `ACTIVE` или `INACTIVE`, пустое значение становится `ACTIVE`.

Пример CSV:
```csv
address,entrance,lift_label,serial_no,lat,lon,status
"Алматы, Абая 10",1,Лифт A,SN-001,43.238949,76.889709,ACTIVE
"Алматы, Толе би 5",2,Лифт B,SN-002,,,ACTIVE
```

Проверки импорта:
- Пустые строки пропускаются.
- Строки без `address` попадают в row-level errors и не создаются.
- `lat` и `lon`, если заполнены, должны быть числами; запятая в дробной части допустима.
- Неподдерживаемые расширения возвращают понятную ошибку.
- Плохой CSV/XLSX не должен ронять приложение; результат показывает ошибки.

Дубли:
- Если указан `serial_no`, он считается главным ключом идентичности.
- Если `serial_no` пустой, дубль ищется по составному ключу `address + entrance + lift_label`, когда все три поля заполнены.
- Текущий импорт **не обновляет** существующие assets. Найденные дубли пропускаются и считаются в `skipped` / `skipped_duplicates`.

Как проверить после импорта:
1. В результате импорта проверьте `created`, `skipped`, `invalid` и row-level errors.
2. Нажмите «Обновить» в реестре или воспользуйтесь поиском по адресу/серийному номеру.
3. Откройте вкладку «Объекты» и убедитесь, что лифты с координатами появились на карте.
4. Скачайте `GET /api/assets/export.xlsx` или кнопку `XLSX`, чтобы сверить загруженный реестр.

## Типовой флоу проверки
1. Запустить сервер.  
2. Войти как admin.  
3. Создать заявку (форма на главной).  
4. Проверить автоназначение мастера и отображение в таблице/канбане.  
5. Скачать архив через кнопку «Скачать архив».
6. Переключиться на masterN, открыть `/mobile`, нажать «Принять», затем «В работу» (для перехода `ACCEPTED → IN_PROGRESS` нужна геолокация и попадание в радиус 500 м от объекта), после работ нажать «Завершить» с обязательной причиной закрытия.
7. Открыть вкладку «Объекты» и убедиться, что точки отображаются из SQL-реестра лифтов, а переключатель «Показывать заявки» показывает открытые тикеты.

## Ручная проверка offline/PWA
1. Онлайн: войти мастером, открыть `/mobile`, убедиться, что назначенная заявка загрузилась и статус синхронизации показывает актуальное состояние.
2. Перевести браузер в offline mode и выполнить поддерживаемые действия: «Принять», «В работу» (если геолокация доступна), «Ожидание», комментарий и фото.
3. Убедиться, что верхний статус показывает очередь, а локальные изменения остаются видимыми после перезагрузки `/mobile`.
4. Вернуть online mode, нажать «Синхронизировать» и проверить, что очередь уходит без дублей: повторный `event_id` должен возвращаться как duplicate/OK, а заявка не должна менять версию повторно.
5. Проверить ошибочный сценарий: конфликт версии или выход за геозону должны остаться в блоке «Требует внимания» с кнопками «Повторить» и «Скрыть», а не исчезнуть молча.
6. Для фото проверить лимиты клиента: файл больше 8 МБ отклоняется до сохранения в IndexedDB, а очередь не растёт выше 20 локальных фото.
7. После синхронизации открыть `/api/me/tickets`, `/api/metrics` и защищённую ссылку `/uploads/<filename>` под разрешённым пользователем, чтобы подтвердить совместимость API, метрик и доступа к вложениям.

## Частые ошибки и решения
- **`Missing dependency: openpyxl` при скачивании архива.**  
  Установите зависимости (`python -m pip install -r requirements.txt`) или используйте встроенный `vendor/openpyxl` (подхватывается автоматически).【F:app.py†L12-L21】【F:app.py†L667-L693】
- **`uploads` нет / ошибка сохранения файла.**  
  Каталог создаётся в `before_request`. Убедитесь, что процесс имеет права на запись в корень проекта или создайте `uploads/` вручную.【F:app.py†L124-L144】【F:app.py†L568-L616】
- **Блокировки SQLite / ошибки записи.**  
  Закройте другие процессы, удалите `lift_crm.db` для сброса (потеря данных), перезапустите сервер. SQLite не рассчитан на высокую конкуренцию.

## Логирование и ошибки
- Логирование: консоль, формат `%(asctime)s %(levelname)s [%(name)s] %(message)s`, уровень по умолчанию INFO; можно переопределить `LOG_LEVEL`.【F:liftcrm/utils/logging.py†L1-L13】
- Ошибки API возвращаются как JSON: `{"error": {"code": <int>, "message": "<string>"}}` для всех 4xx/5xx; для не-API маршрутов остаётся стандартное HTML-поведение. Ошибки логируются с путём и методом.【F:liftcrm/__init__.py†L35-L63】

## Лимитирование логина
- `/api/login` ограничен: 10 попыток за 10 минут на пару `(IP + username)`. Счётчик учитывает все попытки (успешные и неуспешные). При превышении возвращается `429` с JSON-ошибкой `{"error": {"code": "RATE_LIMITED", "message": "Too many login attempts. Try again later."}}` и заголовком `Retry-After`.【F:liftcrm/auth/routes.py†L21-L59】
- Реализация in-memory: состояние хранится в памяти процесса и сбрасывается при перезапуске, а также не разделяется между воркерами/инстансами.【F:liftcrm/utils/rate_limit.py†L1-L34】
- По умолчанию заголовки прокси не доверяются. Если приложение развёрнуто **только** за доверенным reverse-proxy (Nginx/Cloudflare) и недоступно напрямую, включите `TRUST_PROXY_HEADERS=true` (и при необходимости `PROXY_FIX_X_FOR=1`), чтобы `ProxyFix` корректно использовал `X-Forwarded-For`. Иначе оставляйте выключенным, чтобы предотвратить подмену IP.【F:liftcrm/config.py†L7-L20】【F:liftcrm/__init__.py†L23-L38】

## Чек-лист валидации поведения (без изменений)
1. `python -m pip install -r requirements.txt` — зависимости ставятся без ошибок.
2. `python app.py` — сервер стартует, открывается `/` с формой логина.
3. Логин admin/admin123 успешен, `GET /api/me` возвращает role=admin.
4. Создание заявки через форму с выбранным приоритетом → запись появляется в таблице/канбане (`GET /api/tickets`).
5. Переключение приоритета через выпадающий список в таблице обновляет бейдж в таблице/канбане/мастерском UI.
6. Назначение мастера вручную (`POST /api/tickets/{id}/assign/{mid}`) — мастер обновлён.
7. Метрики (`GET /api/metrics`) отвечают корректно под admin/dispatcher; блок «Итоги» показывает распределение по приоритетам.
8. Скачивание архива (`GET /api/archive`) отдаёт `archive.xlsx` с колонкой priority.
9. Вкладка «Объекты» грузит точки из SQL-реестра (`GET /api/assets`), `/api/objects` остаётся алиасом.
10. SLA отображается: создание тикета, ожидание > SLA (или ручная правка времени) → флаги «overdue» в таблице/канбане/дашборде и рост счётчиков в `/api/metrics`.
